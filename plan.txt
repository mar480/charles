The core instruction is:

This branch is now a tagger-first product, not the public taxonomy viewer. The public viewer is already hosted separately and is considered complete. Reuse the existing viewer codebase as the taxonomy/search/details/hypercube foundation for a new iXBRL tagger application focused first on a known Companies House micro-entity template workflow. The viewer and all of its files are included in the repo in the "ada" folder.

The current repository already routes / to the viewer container, so the implementation should deliberately replace the main product route with the tagger dashboard/setup flow rather than treating the tagger as a secondary add-on. The current App routes / to Index, and Index renders XBRLTaxonomyExplorerContainer, which is the existing viewer entry point.

The existing taxonomy viewer functionality should be retained as reusable infrastructure because it already has entrypoint grouping including Companies House forms and Charities SORP, concept selection/navigation props, advanced search state, tree locations, and dimensional relationship APIs.

The backend already includes lxml and arelle-release, so the first implementation should use those for XHTML/iXBRL generation/parsing and local validation rather than inventing a separate validation path.

1. Product objective
Build the first functional version of an iXBRL tagger for Companies House-style accounts, with the micro-entity template workflow as the golden path.

The target user journey is:

User creates a project.

User enters CRN and project defaults.

App optionally fetches Companies House company profile data.

User chooses the mapped micro-entity template.

User manually enters figures, copy-pastes figures, or imports CSV/XLSX.

Template mappings automatically create tagged facts.

User reviews and confirms tags.

App generates iXBRL XHTML.

App checks mandatory tags internally.

App validates with Arelle.

User exports and tests in the Companies House validator.

Manual tagging remains available for corrections and custom documents, but the main product is template-driven auto-tagging, not a primarily manual tagging tool.

Required fixture names
Use these exact names:

fixtures/microentity/microentity-untagged.html

The untagged HTML version of the micro-entity template.

This is the source document the app should load and populate. Do not edit the CSS styles as they are correct for rendering by Companies House post-submission.

fixtures/microentity/microentity-tagged-valid.xhtml

The tagged iXBRL/XHTML version that already passes the Companies House validator.  Do not edit the CSS styles as they are correct for rendering by Companies House post-submission.

This is the golden-master semantic reference.

fixtures/microentity/microentity-fixture-manifest.json

Created by the agent if it does not already exist.

It should describe the expected template ID, taxonomy year, taxonomy entrypoint, periods, default currency, scale, decimals, mandatory hidden facts, field mappings, and comparison strategy.

fixtures/microentity/README.md

Created by the agent.

It should explain how to run the fixture through import, mapping, generation, Arelle validation, and Companies House test-validator submission.

Important fixture rule
If the supplied files contain real company information, the agent should not hard-code those values into the product. The template must be parameterised by project defaults: CRN, company name, dates, director name, authorisation date, dormant/trading status, accounting standard, accounts type, and other required values.

The generated output does not need byte-for-byte equality with microentity-tagged-valid.xhtml. It should match the golden file semantically:

Same required facts.

Same concepts.

Same periods.

Same units.

Same hidden facts.

Same scale/decimals logic.

Same visible template structure where practical.

Same validation outcome.

4. Project setup wizard
The setup wizard is central. It should collect all defaults that will be reused when creating facts, contexts, units and hidden mandatory tags.

Setup wizard sections
A. Company lookup
Fields:

Companies House registered number / CRN.

Company name.

Registered office summary.

Company status.

Company type.

Accounts next period start/end where available.

Accounts last filed type where available.

The Companies House Public Data API company profile endpoint is GET https://api.company-information.service.gov.uk/company/{companyNumber} and requires an API key. The profile resource includes company number, company name, company status, company type, accounts information, accounting reference date, last accounts and next accounts period fields. Source: Companies House API docs. (developer-specs.company-information.service.gov.uk) (developer-specs.company-information.service.gov.uk)

Implementation requirements:

Store the API key in an environment variable.

Never expose the API key to the browser.

Backend endpoint should proxy the lookup.

5. Mandatory tag validation
The app must internally check mandatory Companies House/FRC tags before the user reaches the Companies House validator. It can run silently during editing, but the validation review screen must show any blocking issue clearly before export.

Mandatory checker design
Create:

backend/tagger/mandatory_tags.py
It should define filing-profile-specific mandatory tag sets.

Start with:

companies-house-microentity
companies-house-group-audited
The user-provided list is for group audited accounts, so the system should support that profile, but the micro-entity fixture should have its own mandatory profile based on the golden-master file and Companies House behaviour.

Mandatory tag records
Each mandatory tag rule should include:

{
  "qname": "bus:UKCompaniesHouseRegisteredNumber",
  "label": "UK Companies House registered number",
  "required_for_profiles": ["companies-house-microentity", "companies-house-group-audited"],
  "expected_period": "duration|instant|none",
  "expected_context": "entity|reporting_period|balance_sheet_date",
  "expected_unit": null,
  "source": "project_default|template_field|calculated|user_input",
  "usually_hidden": true,
  "validation": {
    "required": true,
    "non_empty": true,
    "allowed_values": []
  }
}

Entity current legal or registered name.

Average number of employees during the period.

Mandatory checker behaviour
For each mandatory tag, check:

Fact exists.

Correct concept QName.

Required value is present.

Value is valid for its type.

Enumeration/controlled value is allowed where applicable.

Period/context is appropriate.

Unit exists where required.

Decimals/scale are valid where required.

Hidden/visible placement is acceptable.

Fact is not duplicated incorrectly.

Generated namespace prefix resolves correctly.

The source of the fact is traceable to project setup, template field, calculation, or user input.

The validation result should be structured:

{
  "status": "pass|warning|error",
  "ruleId": "mandatory.bus.UKCompaniesHouseRegisteredNumber",
  "qname": "bus:UKCompaniesHouseRegisteredNumber",
  "message": "UK Companies House registered number is missing.",
  "severity": "error",
  "source": "mandatory-tags",
  "relatedFieldId": "project.company.crn"
}

11. Validation pipeline
Create:

backend/tagger/validation.py
frontend/src/components/tagger/ValidationPanel.tsx
frontend/src/components/tagger/MandatoryTagPanel.tsx
Validation layers
Layer 1: Field validation
Runs as the user types.

Checks:

Required values.

Number format.

Date format.

Controlled values.

Negative/positive sign expectations.

Empty-but-required fields.

Layer 2: Template/fact validation
Runs silently during editing and visibly in review.

Checks:

Every required mapped field has a value or accepted nil.

Every mapped fact has concept, period, context rule, unit rule, decimals and scale.

Mandatory hidden facts exist.

Duplicates are intentional.

Calculated/check fields are consistent where possible.

Layer 3: Mandatory Companies House/FRC tag validation
Runs before export and before Arelle.

Uses backend/tagger/mandatory_tags.py.

Must flag missing/invalid mandatory tags before Companies House test-validator submission.

Layer 4: iXBRL generation validation
Checks generated XHTML/iXBRL structure before Arelle.

Layer 5: Arelle validation
Use arelle-release, already in backend requirements.

The output should include:

Severity.

Code.

Message.

Source layer.

Related fact ID.

Related template field ID where possible.

Link to document field where possible.

Layer 6: Companies House test validator
Companies House provides a test validator page for iXBRL submissions. Source: Companies House test validator. (test-validator.companieshouse.gov.uk)

Initial implementation may be manual:

User downloads generated XHTML.

User submits it to the Companies House test validator.

User records pass/fail in the app.

User optionally pastes/upload validator feedback.

If a programmatic route is later available via the Technical Interface Specification, it can be added later.

19. Non-goals for the first one-shot
The agent should not spend the first pass trying to solve every possible filing.

Explicit non-goals:

Fully generic manual iXBRL authoring for arbitrary accounts.

Perfect support for every Companies House template.

Production-grade multi-user SaaS authentication.

Automatic Companies House test-validator submission unless a supported API path is available.

Pixel-perfect reproduction of every supplied XHTML byte.

AI-based concept inference.

Advanced calculation linkbase validation beyond what Arelle already provides.

Replacing the taxonomy engine/viewer internals unnecessarily.
